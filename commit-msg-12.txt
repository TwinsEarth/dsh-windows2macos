docs(account-fleet): the audit that says accounts are not isolated, and the design that would

No code changed. This release is an audit and a design document.

The audit, every line sourced:

  * a device identity is not bound to an account -- machine_id is randomUUID()
  * there is no SN; the concept is not in the codebase
  * there is no hardware identifier in identity or authorisation
  * the relay stores user_id and never reads it (five references, all stores/loads)
  * the plugin never references user_id at all
  * dispatch targets are `all` -- every device on the relay, unfiltered
  * the device table is one flat Map

Measured on the shared relay: devices=4, one pool, one pairing code. Any machine with
that code joins the same pool; any caller with a valid operator token broadcasts to all
four. So the answer to "are accounts mixed into one fleet" is yes, and that is now
written down with the lines that prove it.

The design (docs/ACCOUNT-FLEET-DESIGN.md) covers the three parts asked for: the exact SN
format, the relay authorisation model, and the hand-off timing.

The identity source was verified rather than assumed. DSH already exposes
ctx.deepseekAccount, whose getDeviceIdentity() returns { deviceId?, userId?, osVersion }
and is documented as reading existing login identity without creating a device or
returning credentials. The account identifier therefore needs no account API call -- and a
hand-typed account code in a config row is ruled out, because a value an operator can type
is a value an attacker can type.

Three things the document says that a proposal usually does not:

  1. An SN cannot be a credential. It is client-computed, so anyone who knows an account
     id can forge one. The relay must never trust it, and the timestamp provides no
     cryptographic uniqueness -- uniqueness is (ACCT, HWID). A string scheme presented as
     hardware-grade protection is worse than none, because it is believed.
  2. Hand-off makes execution at-least-once. Fine for `node --test`, not fine for anything
     with write:true, so automatic hand-off is forbidden for writing tasks until a fencing
     token exists.
  3. The relay is the trust root. Compromising it forges any fleet. Accepted, rather than
     adding an online account check that would stop offline machines working.

Nothing is implemented. It lands in v0.8.0 because it changes the relay protocol.
