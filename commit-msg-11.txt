fix(chatops): the fleet reader used the wrong credential and the wrong field names

v0.7.2 shipped a fleet executor that had never been pointed at a live relay. Two guesses
were wrong, both silently, and both are the same mistake as ilink.mjs in v0.7.0 -- one
layer up. A unit suite driving a fake relay cannot falsify its own assumptions about a
real one.

Found by running it against an actual relay and a real Localside agent, which produced:

  [agent] offer 01M4VC7KWKF5WA5Q6BBDNH4AXM attempt 1 {"argv":["node","src/facts.mjs"]}
  [agent] result delivered for 01M4VC7KWKF5WA5Q6BBDNH4AXM {"status":"nonzero_exit"}
  [agent] result accepted for 01M4VC7KWKF5WA5Q6BBDNH4AXM {"status":"nonzero_exit"}

-- the task really ran and really reported -- while the poll loop printed
`verdict=undefined` thirty times in a row.

The two:

  1. GET /v1/tasks/<id> needs the DEVICE token, not the operator token. With the operator
     token it answers
       401 {"code":"UNAUTHORIZED","message":"missing or invalid device_token"}
     Dispatching and reading take different credentials. The executor now holds both, and
     a refusal names which one it wanted rather than reporting a generic 401 -- because
     "your operator token is wrong" and "this install is not paired" have different fixes.

  2. The verdict is not at the top level. It is `body.aggregate.status`, and the
     per-machine rows are `body.leases[]` on a status and `body.machines[]` on a report,
     whose machine field is `machine_name`. The first version read `body.verdict` and
     `body.results`, so every machine printed as `?: ?` while the task completed
     perfectly.

     Measured shape, now the reading:
       status: { aggregate: { status: "unverifiable" }, leases: [{ machine_name, state }] }
       report: { status: "unverifiable", machines: [{ machine_name, outcome, status,
                 exit_code, lease_state, transport }] }

Also: /v1/devices wants the device token too on this relay build, and a lease row carries
`state` rather than `outcome` until the result lands, so `describeMachines` now shows the
outcome when there is one and the lease state when there is not.

Verified end to end against a live relay and a live agent: the executor dispatched, the
agent ran the command on Windows, the result came back, and the corrected reader produced

  任务 01M4VCET — unverifiable
  命令：node src/facts.mjs
  win-desktop: unverifiable  status nonzero_exit  exit 1

which is the relay's own verdict for a command that exited non-zero on an unanchored tree.
272 chatops cases pass.

Still not claimed: no message has been sent from a phone through WeChat to the fleet. The
adapter is verified against live WeChat, and the executor is now verified against a live
relay -- the two have not yet been joined by a human typing.
